# 構成: ネトレ 基本設計レビュー

- テーマ: A / 用途: 社内向け資料 / スタイル: standard / viz: mid / 全 15 枚
- 材料: docs/02_基本設計書.md v0.1（要件定義書 v1.0 反映済み）
- 前提: 手元で読んで記載内容を確認する資料（読み物）。網羅性を優先する
- 設計提案（【要確認】）に D1〜D5 の番号を振り、最終枚でまとめて判断を求める
  - D1 自動生成問題の ID に難易度を入れる（§5.1）
  - D2 次に出す日を日付単位にする（§6.2）
  - D3 正解した自動生成問題は復習の対象にしない（§6.2）
  - D4 問題の version が上がっても履歴を引き継ぐ（§6.2）
  - D5 入力式の回答を正規化して比べる（§6.3）

## スライド 1: 表紙
- レイアウト: 型 H（上下にドット帯）
- なぜこの形か: 直前のデッキ（要件定義）が型 G のため、同じ型を続けない。型 E も検討したが、シリーズとして落ち着いた H にした

## スライド 2: 結論 — v1.0 の作り方
- レイアウト: 紺ブロックに 1 文 + 数字の行
- なぜこの形か: 要件定義デッキと同じ「結論を最初に」の型。数字で設計の規模を示す

## スライド 3: システム構成と採用技術
- レイアウト: 左に端末内の構成図（HTML の枠）、右に採用技術の表
- なぜこの形か: 構成図だけだと採用理由が落ちる。表だけだと「外部通信なし」が伝わらない

## スライド 4: アーキテクチャ
- レイアウト: 4 層を縦に積む ladder + 右にフォルダ構成
- なぜこの形か: 依存の向き（上から下だけ）は積み上げで見せるのが最短。card grid 案は向きが消えるので退けた

## スライド 5: 要件と構成要素の対応
- レイアウト: 表
- なぜこの形か: 対応表の確認が目的。図にすると要件 ID が追えない

## スライド 6: 画面一覧と遷移
- レイアウト: HTML ピル + 矢印（§8-H）
- なぜこの形か: 遷移は順序。表では流れが消える

## スライド 7: 問題データと問題 ID
- レイアウト: 種類の 2 列 + ID 形式の表 + 提案 D1 の枠

## スライド 8: 学習履歴のデータ
- レイアウト: 2 エンティティの表を左右に並べる
- なぜこの形か: 1 枚の表に混ぜると、どちらの項目か分からなくなる

## スライド 9: 学習の組み立て
- レイアウト: 左に 2 段の手順、右に出題範囲の表

## スライド 10: 間隔反復
- レイアウト: 間隔の伸び方をピルの連鎖で + 提案 D2・D3 の枠

## スライド 11: 回答の判定と問題の修正
- レイアウト: 左に入力式の正規化 3 段（D5）、右に version の方針（D4）

## スライド 12: 自動生成問題の品質
- レイアウト: 表（T-1〜T-4）

## スライド 13: エラー処理
